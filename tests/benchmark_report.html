The WebGL2 build is non-functional in headless Chrome. step_frame returns in <1ms without doing real work (52,380 calls in 15s). perfStats is null, nonblack_pixels is -1. The page likely fell back to the software renderer or the WebGL2 context creation failed silently in headless mode. This needs a visible (non-headless) Chrome to test properly.

The boot-sequence numbers were worthless. During boot, the 3DS firmware loads code into memory, initializes services, and sets up the GPU — all of which the interpreter handles quickly with minimal rendering. Once actual gameplay begins (save state restore), the software renderer's GPU emulation dominates at 210ms per vblank. This is the real bottleneck, not the ARM interpreter.

The ARM interpreter (which the WASM caching patch targets) accounts for a negligible fraction of the 267ms vblank interval. The software GPU rasterizer is the dominant cost. Optimizing ARM execution alone cannot fix performance — the GPU pipeline needs acceleration (WebGL2 hardware rasterization) to make the emulator playable.

WASM Caching Patch: Verdict

❌
No measurable impact possible with current bottlenecks
Even if ExecBlock and WASM JIT were fully functional, the ARM interpreter is not the bottleneck. The software GPU rasterizer consumes 210ms per vblank — over 75% of the frame budget. Making ARM execution 2× faster would only reduce the interpreter slice from ~56ms to ~28ms, improving overall speed from 6.3% to maybe 7-8%. The emulator needs GPU hardware acceleration (WebGL2) to reach playable speeds.
